# Astro 迁移验证方案（基线清单）

基于 commit `07a4795` 的 `index.html`（915KB / 7296 行）生成。迁移过程中任何一项对不上，即说明有遗漏。

## 检查体系一览（本文档的规范称呼）

本文档不用内部代号行文；提到自动检查时统一使用下表的名称。脚本文件名沿用历史的 `layerN` 编号，仅作为文件名。

| 检查名称       | 命令               | 脚本                        | 检查什么                                                                                                                   |
| -------------- | ------------------ | --------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 结构检查       | `verify:structure` | layer1-structure.py         | 构建产物与原版页面骨架一致（元素 id 集合、头部/页脚、CSS、单文件打包、无转义膨胀）                                         |
| 行为比对       | `verify:behavior`  | layer2-behavior.mjs         | 同一随机数种子下新旧输出逐字节一致；日语场景对照冻结原版，英/中场景对照基准快照（有意改动显示时用 `--update-golden` 重录） |
| 截图比对       | `verify:visual`    | layer3-4-visual-storage.mjs | 设置页截图一致（登记在案的有意差异除外）                                                                                   |
| 存量数据检查   | 同上               | 同上                        | 旧版本存下的浏览器数据在新版中完整可用                                                                                     |
| 数据表核对     | `verify:data`      | layer5-data-equal.mjs       | 数据常量与冻结基线深度相等；部分表为子集模式（基线条目不许改删、允许新增）                                                 |

## 0. 项目形态（迁移对象）

单文件、零依赖的纯客户端应用：

| 区段       | 行号     | 内容                                                                                                                       |
| ---------- | -------- | -------------------------------------------------------------------------------------------------------------------------- |
| `<head>`   | 1–6      | `lang="ja"`、charset、viewport、`<title>Guzen Ikemen Maker V3.0.0</title>`（无 favicon、无任何 `<link>`/meta description） |
| `<style>`  | 7–129    | 唯一样式块，约 200 条规则                                                                                                  |

已确认为**零**的项（迁移后也必须为零）：外部请求（fetch/XHR/WebSocket）、外部资源（CDN/图片/字体/`<link>`）、`DOMContentLoaded`/window 级监听、HTML 注释、内联事件属性（`onclick=`）、URL/query 参数处理、`<noscript>`、print 样式。

## 1. 验证策略：多层自动检查

### 结构检查（`verify:structure`，layer1-structure.py）— 结构等价（静态 diff，全部可脚本化）

对「原 index.html」和「Astro 构建产物 dist/index.html」各跑一遍提取脚本，集合必须相等：

```bash
# id 集合（基线 176 个，无重复）
grep -o 'id="[^"]*"' <file> | sort -u

# data-* 属性名集合（基线 32 个，见附录 C）
grep -o 'data-[a-z-]*[=" ]' <file> | sort -u

# localStorage key 必须原样存在
grep -c "guzen-ikemen-maker-v1.results\|guzen-ikemen-maker-v1.presets" <js>

# head 四要素字节级一致
grep -c 'lang="ja"' ; grep -c '<meta charset="utf-8"' ; grep -c '<title>Guzen Ikemen Maker V3.0.0</title>'

# 页脚版权行字节级一致（注意混用的半角 ( 和全角 ）括号）
grep -c '© DAZ_だいすけ：FOOTHOUSE(AI男子） / Guzen Ikemen Maker V3.0.0'

# 构建后的 CSS 不得被 Astro scope 化
! grep -q ':where(.astro-' dist/**/*.css dist/index.html

# 超长数据行未被格式化工具重排（NAMES_BY_YEAR 单行 10,898 字符）
awk 'length($0)>10000' <js> | wc -l   # 基线 ≥1
```

数据表逐一比对：若把常量抽成模块，写一个 Node 脚本把「旧文件中提取的常量」与「新模块导出」做 deep-equal（深度相等比较），并核对附录 A 的条目数（例如 `Object.keys(pools).length === 100`、`OCCUPATIONS.length === 100`、`valueTranslations` 829 个唯一 key、`NAMES_BY_YEAR` 26 个年份）。

### 行为比对（`verify:behavior`）— 行为等价（同一随机数种子下新旧输出逐字节比对，最可靠的一道检查）

全应用的非确定性来源只有三处，全部可在测试里固定：

- `Math.random`（生成逻辑全部依赖它）
- `Date.now()` — 仅 `uniqId()`（549 行）
- `new Date().toISOString()` — 仅 `createdAt`（5722–5725 行）

用 Playwright 的 `addInitScript` 在**旧页面和新页面**注入同一个带种子的 PRNG（伪随机数生成器，如 mulberry32；种子即随机数种子，同一种子必然产出同一串随机数）替换 `Math.random`，并把 `Date.now`/`Date` 固定为常量，然后：

1. 勾选「instant mode」→ 点 SLOT START；
2. 抓取 7 个 prompt textarea 内容 + `#profileView` 的 innerHTML + rarity 分数；
3. 新旧两边**逐字节比对**；
4. 循环 ≥50 个种子 × ja/en 两种 UI 语言 × 4 种生成模式（full/face/outfit/rare）。

任何数据表被漏抄一行、任何函数被重排（见风险 8），比对立刻发现。这项检查是唯一能证明「6900 行生成逻辑没有发生语义漂移（行为悄悄变化）」的手段。

### 截图比对（`verify:visual`）— 界面外观回归

断点在 `@media 980px`（×4）、`@media 760px`、`@container 560px`，所以至少两个视口（390px 移动、1280px 桌面）× 4 个主 tab × ja/en，新旧截图做逐像素比较。注意：`initialCard` 子卡片静态标记里有 `class="hidden"` 但启动时被 `syncCardSettingsVisibility()` 无条件显示——像素对比必须以**运行后**状态为准，不能拿静态 HTML 说事。

### 存量数据检查 — 老用户数据兼容

1. 在旧版本保存一条历史 + 一个预设；
2. 同一浏览器、同一 origin 打开迁移后的构建产物；
3. 历史面板必须列出旧记录，预设下拉必须出现旧预设。

⚠️ localStorage 按 origin 隔离：换域名/子域名、或从 `file://` 换到服务器，老数据都拿不回来。路径变化（`/` → `/guzen/`）安全。上线前想清楚部署 origin。

## 3. 建议的迁移路线（让验证可行）

- **Phase 1 — 原样搬运（lift-and-shift）**：一个 Astro 页面，body HTML 逐字节复制，`<style is:global>` 原样，JS 原样放 `public/app.js` 用经典 `<script src>`（或 `is:inline`）在 body 末尾引入。此时 dist 与原文件可近似 diff，各项自动检查全部跑通后 commit。已知局限：还没享受任何 Astro 组件化好处——但这是零遗漏风险的锚点。
- **Phase 2 — 数据抽离**：146 个常量逐个（或按组）抽成模块，每抽一个跑深度相等比较 + 行为比对。注意风险 8 的函数不许动。
- **Phase 3 — 组件化拆分**：HTML 拆组件，每步跑结构检查的 id/data-\* 集合 diff + 截图比对。

每个 Phase 结束提交一次 commit（不要直接提交到 main，先开分支）。

### 4.1 启动条件（二选一，缺一不启动）

1. 原作者停止更新单文件原版；或
2. 决定与上游分道扬镳，此后功能开发都在 Astro 版进行、不再跟进上游。（**已满足**）

**理由**：现在 `app.js` 是从 `index.html` 机械提取的，上游更新的同步成本 = 一次 merge + 一次管线重跑（V3.0.0→V3.2.0 实测零手工修改）。模块化是语义级重构、无法机械化——做完之后同步管线即断，上游每发一版都要人肉移植 JS diff（V3.0.0→V3.2.0 一次就是 ±700 行）。在上游活跃期做 Phase 4，维护成本不可持续。

### 4.2 做什么（按顺序，每步独立验证、独立 commit）

1. **冻结基线**：宣布 `index.html` 基线冻结（记录冻结时的上游 commit）；phase1–3 提取脚本转为「一次性历史工具」归档；数据表核对的对照基线从 `index.html` 切换为冻结时的 `public/data/*.js`。
2. **清死代码**：删除 7 组同名函数中**被覆盖的早期定义**（约 500 行，V3.2 时代的旧实现，位置见风险 #8；V3.2.0 同步后行号有漂移，以 `grep -n 'function <名字>'` 现查为准）。行为不变的依据：函数声明提升让后者本来就赢——删除前后，行为比对的 100 个场景必须逐字节一致。顺带清理幽灵引用（`cardPromptBox`）和无样式类（`.faved`——决定是补样式还是删写入）。
3. **strict mode 预检**：在 IIFE（立即执行函数包裹）首行加 `'use strict';` 构建一版，跑行为比对全量 + 扩充场景（JSON 导入/导出、复元コード、预设增删、slot 编辑器、sportsHistory 编辑器——现有套件没覆盖的交互），抓隐式全局赋值等只有在非严格（sloppy）模式下才跑得通的写法。全部通过后再进入下一步；此步本身可以合并（strict IIFE 是合法增强）。
4. **拆模块**：按主题切分——`data/`（数据访问，替代 window.GUZEN_DATA 桥接，public/data 移入 src/data 转 `export const`）、`gen/`（角色生成、权重抽取、rarity）、`prompt/`（各 prompt 构建器 + 翻译）、`ui/`（渲染、slot 编辑器、tab/accordion）、`storage/`（localStorage、导入导出、复元）、`i18n/`、入口 `main.js`（事件绑定 + init 顺序，保持现有 init 次序不变）。函数体零改动，只动归属和 import。
5. **打包决策**：交给 Astro/Vite 打包（`<script>` 不再 is:inline）。两个已知坑的对策：esbuild 把日文转义成 `\uXXXX` → `vite: { esbuild: { charset: 'utf8' } }`；模块脚本默认延迟执行（deferred）→ DOM 查询本来就在函数内或 init 时执行，末尾 init 调用在 module 里等价成立，但需行为比对确认无时序回归。
6. **验证体系随之调整**：行为比对、截图比对、存量数据检查原样保留（行为级，old = 冻结的 index.html，永久有效）；结构检查（`verify:structure`，layer1-structure.py）重写（script 标签变成带 hash 的 module、不再做 JS 的 verbatim（逐字原样）检查，改为「构建产物无 \uXXXX 膨胀、无多余外部请求」）；数据表核对改为对照冻结基线的数据模块。**行为比对是本 phase 唯一的裁决标准**——每个 commit 都必须 100/100。

### 4.3 风险清单（沿用第 2 节编号）

风险 #1（strict mode）由步骤 3 前置化解；风险 #8（同名函数）由步骤 2 前置化解；风险 #4（格式化）在模块化后解除（数据模块可以正常格式化，届时缩减 `.prettierignore`）；新增风险：Vite 代码分割可能改变模块求值顺序——入口显式 import 并保持 init 在最后，靠行为比对兜底。

### 4.4 预估

步骤 1–3 各半天内；步骤 4–6 合计 2–4 天（312 个函数的归属划分是主要工作量）。全程只要行为比对保持通过，即可安全中断/回滚——每步独立 commit 保证任意点可停。

## 7. 上游 V3.2.1 / V3.2.2 移植（2026-08-06）

### 7.1 方法：把基线重新锚定为移植的验证器

## 10. i18n 实现审查与有界清理（2026-08-07，分支 `i18n-cleanup`）

用户问「i18n 的实现方式是否需要重构」。先做量化盘点，再据此决定动多少。

### 10.1 盘点结论：架构不用重构

| 机制                                      | 调用量    | 状态                              |
| ----------------------------------------- | --------- | --------------------------------- |
| `T('key')` → `uiText[lang]`               | 240       | 三语各 107 条，**零缺失**         |
| `displayValue()` / `displayOptionLabel()` | 231       | 单一扁平表 `VALUE_I18N`           |
| `LT(ja, en, zh)` 内联                     | 145       | **全部传满 3 参**，无静默回落日文 |
| `english` 布尔参数（提示词侧）            | 77 个函数 | 正确建模，见下                    |
| 裸 `ST.uiLang===` 内联分支                | 56        | 主要挤在 ui.js 超长行里           |
| 专属 `*_ZH` 侧表                          | 9 个导出  | 见 10.3                           |

**最初怀疑那 77 个 `english` 布尔参数是技术债，查下来不是**：`pools.promptLanguages === ["日本語","English"]`，**提示词语言天生只有两种**（由 `isEnglish(c)` 驱动），**界面语言才是三种**。这是有意设计的双轴模型（提示词语言、界面语言各一条轴），布尔在提示词侧是正确的，不该改成三态。

也专门查了最危险的情形——有没有谁把 `ST.uiLang` 直接塞进 `english` 参数（那会让中文用户看到英文）：**0 处命中**。所以现状是「看着杂、实际自洽」。

### 10.2 清理一：消除「把字符串 `'zh'` 当布尔参数传」

同时横跨两条语言轴、身兼两职的函数原先这样调用，重复 8 次：

```js
sportsHistoryText(ST.current, ST.uiLang === "zh" ? "zh" : ST.uiLang === "en");
```

字符串 `'zh'` 是真值（非空字符串在布尔判断中为真），所以**任何只认布尔的函数一旦被这样调用就会静默返回英文**。而且这个三态表达式本身是把 `ST.uiLang`（本就是 `'ja'|'en'|'zh'`）做了一次**有损的重新编码**。

**首轮只找到 7 个身兼两职的函数，穷尽扫描后是 8 个**——`underwearDesc` 漏了，因为 `ui.js:88` 直接传字面量 `'zh'` 而非那个三态表达式。补扫方式：解析所有调用的**末位实参**（按括号配对解析，而不是用正则逐行匹配），列出以 `'zh'` 或含 `uiLang==='zh'` 为末参的被调函数。

改法：8 个函数签名 `english=false` → `lang='ja'`，函数体首行派生 `const zhMode = lang === 'zh', enMode = lang === 'en';`。

> **关键陷阱**：不能只把 `english` 改名 `lang`。函数体里 `return english ? EN : JA` 是**真值判断**，而 `lang` 恒为真（`'ja'` 也是真），直接改名会让日文模式返回英文。必须先派生显式布尔再替换。

47 个调用点按 5 种形态映射成显式语言码：`false`→`'ja'`、`true`→`'en'`、三态表达式→`ST.uiLang`、`ST.uiLang==='en'`→`ST.uiLang`、透传 `english`→`langOf(english)`。

新增 `langOf(v)`（i18n.js）把提示词侧的布尔转换成语言码，供 3 处透传调用者使用。**最终态：每个函数只吃语言码或只吃布尔，绝不混用。**

### 10.3 清理二：`INNER_LABEL_ZH` 是唯一的例外岛

`inner.js` 里 43 行、44 处走侧表 `LT('JA','EN', INNER_LABEL_ZH['JA'])`，而全项目另外 145 处 `LT()` 都把三种语言内联在调用点。这是上一轮批量代码改写处理 44 个三元表达式留下的产物，不是设计。已全部折回内联写法，`INNER_LABEL_ZH` 的数据导出与数据表核对的白名单条目一并删除（`*_ZH` 导出 9 → 8）。

**为何不顺手把余下 8 个 `*_ZH` 表并进主表**：验过它们与主表**零键冲突**（唯一真冲突是 `SPORT_MUSCLE_ZH`，键是运动名而值是肌群描述，语义域不同，必须独立）。但只把 zh 抽进表、en 仍留在 `LT()` 参数里会造成不对称，比现状更糟——`LT()` 的价值恰恰是三种语言都摆在调用点、可 grep、自解释。

### 10.4 第三项（56 处裸 `ST.uiLang===`）有意不做

价值低、风险高——都在 ui.js 最脆的超长行里。等将来因别的原因拆那些行时顺手做。本轮顺带消掉了 17 处（三态表达式那批），剩 39 处。

## 14. i18next 运行时（2026-08-12，分支 `i18next-runtime`，叠于 §13 之上）

**动机与定位**：应「用框架治理漏翻译」的诉求迁移到 i18next（26.x），但采用**以日语原文本身作为查表键**的模型（即 gettext 的 msgid 做法）——日语串既是内部表示也是查表键，`src/data` 的翻译表**仍是唯一事实源**，i18next 资源在初始化时从表构建。因此数据表核对的钉扎、上游逐行可 diff 性、翻译表对账全部原样有效；框架带来的增量是 **dev 模式的 saveMissing 落空收集器**（saveMissing 是 i18next 的选项：查不到译文时把缺失键上报，此处收集进 `window.__i18nMissing`；静态清单管全集、运行时埋点管漏网，与翻译表对账互补）。

**机制**（`src/app/i18n-runtime.js`，仅依赖 i18next + `src/data`，Node 可直接 import）：

- 命名空间（namespace，i18next 给翻译资源分组的单位）分为 `ui`（uiText 三语）/ `values` / `scenes`（仅 en/zh——ja 即原文，无「ja 译文」概念）；`fallbackLng:'ja'` 只对 `ui` 生效；
- **配置纪律**：`keySeparator`/`nsSeparator` 关闭（键含 ASCII `16:9`、`×0.5`）；插值与嵌套前后缀钉为 `⁅⁅`/`⁆⁆` 这类哨兵字符（正文中不可能出现的标记；含 `{{ }}`、`$t(` 的译文因此原样返回，已用敌意串验证）；`returnObjects` 开（`T('rows')` 等返回子表）；`returnEmptyString:false` 对齐旧 `|| v` 语义；`initImmediate:false` 同步初始化不动启动顺序；
- **两种查法**（对应旧代码两种语义，不可混用）：`valueT`（**精确 `vt[String(v)] ?? v` 语义**——miss 返回**原值**而非串化 key，undefined/0 原样透传，miss 手动进收集器）用于 `promptValue`；`valueRes`/`sceneRes`（getResource 型，missing→undefined）用于 `vt[a] || vt[b] || c` 链和存在性守卫——**空键必须返回 undefined**：`getResource(lng, ns, '')` 会返回整个命名空间对象，穿搭笔记等字段常年传空串，首轮行为比对就靠 30 个基准快照 diff 抓出了 `[object Object]`（修复后 144/144 恢复逐字节一致）；
- `i18n.js` 的 `T`/`displayValue`/`displayOptionLabel`/`promptValue`/`sceneDisplay` 改走上述助手；`promptValue` 硬钉 `'en'`（双语言轴纯度不变）；`generate.js`/`prompts.js` 的 prompt 轴内联直查**有意不动**（同一张表，行为等价，Phase 2 再议）。

**验证**：等价性扫描 12,608 断言零失配（全表键 × 三语言 × 新旧两种查法 + 未知键/空键/非字符串输入/分隔符高危键/敌意插值串）；全部自动检查通过，其中 **行为比对 144 场景（106 日文基线 + 38 基准快照）逐字节零差异**——迁移忠实性的金标准。四视角对抗审查（i18next API 语义/调用点/构建产物/语言轴）另抓出并已修复：① `valueT` 曾用 t() 实现丢失 `?? v` 语义——`promptValue(undefined)` 返回 truthy 字符串 `'undefined'` 击穿下游 `|| ''`/`|| 'man'` 兜底（旧版导入 JSON 缺 season/role 时英文 prompt 出 "Season: undefined."），改为 getResource + 原值回退；② `saveMissingTo` 默认 `'fallback'` 会把所有 miss 标成 `ja`，改钉 `'current'`；③ dist 曾滞后于源码（嵌套哨兵未入 bundle），已重建。

**已知局限**：① saveMissing 只见**渲染过的**表面（与界面残留扫描同盲区），全集保障仍靠翻译表对账 + 未来的词库登记表；② 收集器 dev-only，需人工读取 `window.__i18nMissing` 导出，尚无自动回灌流程；③ 标签映射表（slotLabelMap 等 5 表）与 `LT()` 内联三元未入 i18next（表已被翻译表对账的标签映射表核对全覆盖，收益为零）；④ bundle 增重约 i18next 体积（单文件打包内联，无外部请求，结构检查钉扎）。

## 15. 待翻译词汇总清单（2026-08-13，分支 `i18n-word-inventory`）

**动机**（残留清零计划第 1 步）：此前没有一份「哪些词需要翻译」的总清单——翻译表对账只能比较英文表和中文表，一个词**两种语言都没翻**时没有任何记录知道它存在（`ベンチのある床`、`勤務中` 就是这么漏的）。本步把「会显示到界面上的词库」登记造册，让应译集合变成机器可枚举的。

**摸底**：用并行 agent 逐一追踪全部 133 个数据导出在 `src/app` 里的用途并人工复核——92 个属于显示类（值经档案行/下拉选项/编辑器词库直接显示）、36 个豁免（人名词库、纯 ASCII、权重配置、翻译表自身）、5 个只进提示词不进界面。三类明确不进值表清单并写明理由：宣传语素材池（值只拼进整句、表条目治不了，残留清零计划第 4 步在生成器侧解决）、只进提示词的值、人名词库。

**机制**（`verify/i18n-pool-registry.mjs` + 翻译表对账新增检查段）：

- **词库覆盖**：清单内每个含日文的值必须同时在英文表和中文表（场景句池对场景表）；纯 ASCII 值自动豁免（原样显示即正确）。存量缺口冻结进欠账台账 `verify/golden/pool-gap.json`，纪律与英文欠账台账一致（文件缺失/损坏即报错、只能 `--write-baseline` 显式重建、补齐后自动收紧并要求提交）。
- **键对账**：翻译走专用映射表的词库（槽位标签、足部配置轴、好友关系/上下关系）检查「每个键语言齐全」，缺键直接报错——槽位标签缺键正是 2026-08-13 修过的真缺陷，今后再犯当场拦截。

**台账初始规模**（2026-08-13 冻结）：英文缺 1621 个显示值 + 498 条场景句；中文缺 321 个显示值（主要是内在资料词库，即残留清零计划第 3 步的量化范围）+ 0 条场景句。

**上线当天抓到的真缺口**：好友上下关系 `同期`（`fixedHier` 值）在英/中映射表里都没有，好友行直接显示日语原文——已补（英 Same cohort / 中 同期入职）；`FRIEND_HIER_EN` 是冻结基线常量，数据表核对的子集白名单相应加入。

**验证**：变异测试 3/3——词库塞新日语值（双语都不翻）、slotDefs 加无标签槽位、台账文件损坏，全部被当场拦截；全部自动检查通过（行为比对 144 场景零差异——`同期` 补译未被任何基准快照场景抽中）。

**已知局限**：① `src/app/main.js` 在运行时给 `SPORT_MUSCLE` 等追加的词条，静态清单取不到——由第 2 步的运行时落空收割兜底；② 宣传语素材池（约 297 条短语）不在清单内，属第 4 步生成器侧工程；③ 清单登记依赖人工判定「是否显示」，新增数据文件时需要同步登记（登记漏了检查就看不见——这是清单机制的固有边界）。

## 16. 运行时漏翻检查 + 扫描盲区补齐（2026-08-13，分支 `i18n-runtime-check`）

**动机**（残留清零计划第 2 步）：静态检查（翻译表对账、词库总清单）看不到两类东西——生成器现场拼装的句子（内在资料、宣传语，没有任何表能静态对账）和硬编码在代码里的字面量。此前应用已内置「查不到翻译就记一笔」的收集器，但只在开发模式生效、要人工打开浏览器控制台看，等于没有消费方。本步把它接进自动检查。

**机制**：

- **运行时开关**：网址加 `?i18ndebug` 即可在构建产物上开启收集（`src/app/i18n-runtime.js`）；不带参数时行为与线上完全一致——行为比对 144 场景零差异是证明。
- **字段级对账**（`verify/layer8-runtime-missing.mjs`，`verify:missing`，已入 `npm run verify` 链）：固定随机数种子，真实操作页面（英/中 × 4 种职业，展开内在资料、三种派生面板、全部行编辑器和槽位编辑器），收割「查不到翻译**且值里含日文**」的字段（纯 ASCII 值原样显示即正确，不算漏翻）。对账粒度是**字段**（如 `zh:values:innerText`）而非精确词条——拼装句含随机姓名/日期，词条级台账在随机序列变化后会大面积假报警；字段名有限稳定，且直接指出「哪个显示位置在漏」。精确词条仍在 `window.__i18nMissing` 供人工排查。
- **台账** `verify/golden/runtime-missing-fields.json`：121 个字段（英 70 / 中 51；中文侧几乎全是内在资料行——第 3 步的精确地图）。纪律与其他台账一致。
- **扫描盲区补齐**：界面残留扫描的区域清单补上 `.slot small`（槽位磁贴标签——上周「肌の特徴⑴」裸奔的位置），无假阳性。

**上线首日的收获**：收割当场发现 `flow.js:731` 硬编码的 6 条穿搭笔记编辑器候选项不在词库总清单里（硬编码字面量正是静态清单的固有盲区）——已补登记，词库台账相应 +6/侧。

**验证**：变异测试——删掉一个干净字段的中文词条（眼睑 `一重`），检查当场报出新字段 `zh:values:eyelid`；重跑两次收割结果逐字段一致（种子固定保证确定性）；全部自动检查通过。

**已知局限**：① 收割覆盖 4 种职业 × 固定种子的一条操作路径，没走到的界面状态（特定职业专属面板等）可能有字段漏收——扩职业清单即可扩覆盖；② 字段级对账意味着「同一字段里新增一个漏翻词条」不报警（字段已在账上）——词条级的保障由词库总清单负责，两者互补；③ 台账里的 `name` 字段是人名回退（产品设计），留账不修。

## 17. 内在资料中文化·试点批：显示时模板匹配引擎 + 基础信息行（2026-08-14，分支 `i18n-inner-templates-1`）

**动机**（残留清零计划第 3 步第一批）：内在资料的拼装句存储的是成品日语串（`c.incomeText` 等），且下游逻辑会用正则反解析这些串——存储层必须保持日语。因此翻译只能在**显示层**做，而显示层拿到的是含随机数字/零件的成品串，查值表必然落空。

**机制——显示时模板匹配**（`src/app/i18n-runtime.js` 的 `tryTemplate` + 句式表 `src/data/data-i18n-templates.js`）：

- 句式表沿用「日语原文即查表键」模式：键 = 占位化的日语句式（`年収 約{n}万円`），值 = 中文句式。`{n}` 数字变量原样回填；`{w}` 文本变量先查值表、再**递归**试句式表（和历「平成{n}年」就是嵌套句式），查不到用原文并上报收集器——字段因此留在运行时漏翻台账上，直到零件也翻齐；
- 挂在 `displayValue`/`displayOptionLabel` 的查表落空路径上：**生成器一行不改**（上游可 diff 性完整保留）、存储层不动（历史存档和导入的旧 JSON 同样被翻译）；
- 长句式优先匹配（泛化形状 `{w}：{w2}` 排在带后缀的特化形状之后）。

**试点批内容**（出生年月日/出身地/血型/学历/年收 5 个字段）：穷举工作流枚举 5 个生成函数的全部输出形状 → 14 条句式 + 268 条词表（星座/干支/和历/都道府県/城市/国名/学历/收入句）+ 68 条固定句登记进词库总清单。

**台账变化**（三本账同时收紧）：词库覆盖中文侧 327→157（−170）；运行时漏翻中文侧 51→46 字段（试点 5 字段全部清零）；编辑器池 581→474（−107，泛化句式顺带把其他字段的组合值零件也翻了）。

**验证**：行为比对 144 场景零差异（日语路径逐字节不动——引擎只在非日语的落空路径生效）；中文基准快照按流程重录；全部自动检查通过。

**已知局限**：① 句式必须与生成器输出逐字符一致，生成器改句式时匹配会静默失效——运行时漏翻检查会把失配暴露为字段回归；② 泛化句式 `{w}：{w2}` 会部分翻译其他字段的组合值（零件翻了、前缀没翻）——输出只会更好不会更差，且字段仍留在台账上直到全翻；③ 中文译文为机器起草待仓库主人审校（对照表随 PR 提供）。
